# 05 — Spring Boot Q&A

Cover the answer, say your version out loud, then compare.

---

## A. Core

**A1. What is Spring Boot?**
> "Opinionated Spring: auto-configuration, starter dependencies, an embedded server, and
> externalized config. It lets me build a runnable service with a single `main` and focus on
> business behavior instead of wiring."

**A2. What is dependency injection?**
> "A class declares its dependencies; the container provides them. Constructor injection is
> preferred because dependencies are explicit, final, and easy to replace in tests."

**A3. What do `@RestController`, `@Service`, and `@Repository` do?**
> "They are stereotypes that mark beans and convey intent. `@RestController` handles HTTP and
> serialization, `@Service` holds business logic, `@Repository` handles persistence and translates
> exceptions. The behavior is similar; the intent and exception translation differ."

**A4. How does auto-configuration work?**
> "Spring Boot inspects the classpath and properties and configures beans with sensible defaults.
> I can override with my own bean, properties, or exclude an auto-configuration. It is real wiring,
> so integration tests should verify the actual context."

**A5. How do profiles work?**
> "Named configuration sets. `application-{profile}.yml` overrides the base config. I activate a
> profile per environment and test with the profile used in the target environment, so a
> profile-specific wiring bug is caught before release."

**A6. What is `@SpringBootApplication`?**
> "A convenience annotation combining `@Configuration`, `@EnableAutoConfiguration`, and
> `@ComponentScan`. It bootstraps the app and scans the package and subpackages."

**A7. How do you externalize configuration?**
> "Properties/YAML, environment variables, command-line args, and typed `@ConfigurationProperties`.
> Secrets come from a secret store, not the repo. Required config should fail fast at startup."

**A8. What is Actuator?**
> "Operational endpoints: health, info, metrics, env, loggers. I expose only what is needed, protect
> sensitive endpoints, and use health/readiness probes in release validation."

## B. REST design

**B1. How do you design a REST API?**
> "Resources as nouns, methods matching semantics, correct status codes, a stable error model,
> validation at the boundary, pagination caps, idempotency for retried writes, and versioning only
> when necessary. The contract should be testable and documented."

**B2. What status code for create/delete?**
> "Create returns 201 with a `Location` header. Delete returns 204 if there is no body, or 200 if I
> return a representation. The key is consistency and documentation."

**B3. What is idempotency and how do you implement it?**
> "A retried request has the same effect as one request. For POST, accept an `Idempotency-Key`,
> store the key and result, return the stored result on retry, and reject the same key with a
> different payload. Test duplicate and concurrent requests."

**B4. How do you paginate?**
> "Offset pagination for simple/admin cases; cursor pagination for large or real-time data. Cap the
> page size server-side, define a stable sort, and test first/last/beyond-end/invalid cursor."

**B5. How do you model errors?**
> "A stable machine-readable `code`, a human message, the path, field errors for validation, and a
> trace ID. Do not leak stack traces. Clients should branch on `code`, not parse prose."

**B6. How do you version an API?**
> "Prefer additive, backward-compatible changes. If I must break, use a URI/header/media-type
> version, document the deprecation, and give consumers a migration window."

**B7. How do you validate input?**
> "Bean Validation at the boundary (`@Valid`, `@NotBlank`, `@DecimalMin`), plus business validation
> in the service. Return 400 with field-level errors. Test boundaries, missing fields, wrong types,
> and malicious input."

## C. Persistence

**C1. Why keep entities out of the API?**
> "Entities are persistence models; DTOs are the API contract. Returning entities couples the API to
> the schema, leaks lazy-loaded fields, and makes backward-compatible changes harder."

**C2. How do transactions work?**
> "`@Transactional` wraps a public service method in a transaction. Unchecked exceptions roll back by
> default; checked exceptions do not unless configured. Keep transactions short and do not call slow
> external services inside them."

**C3. What is the N+1 problem?**
> "One query for the parent list plus one query per parent for a lazy association. It is correct but
> slow. Fix with `JOIN FETCH`, `@EntityGraph`, batch fetching, or a DTO projection, and test query
> count/latency as the parent count grows."

**C4. How do you manage schema changes?**
> "Flyway or Liquibase migrations, versioned and immutable. Use expand/contract for zero-downtime:
> add, backfill, switch, remove later. Test against production-like data and measure lock time."

**C5. H2 vs Testcontainers?**
> "H2 is fast for slices but not production SQL parity. Testcontainers runs the real database, so I
> use it for dialect, migrations, constraints, and transaction behavior. I don't assume H2 behavior
> equals Postgres."

**C6. How do you test repository queries?**
> "`@DataJpaTest` for fast mapping/query tests, Testcontainers for real dialect and migrations.
> Assert persisted state and query results, not SQL strings."

## D. Testing

**D1. How do you test a Spring Boot controller?**
> "`@WebMvcTest` with MockMvc, mocking the service. Assert status, headers, body, validation errors,
> and the error handler. It is fast and focuses on the HTTP contract."

**D2. When do you use `@SpringBootTest`?**
> "For full wiring, real HTTP, security filters, transactions across layers, and profile-specific
> config. I keep the number small because context startup is expensive."

**D3. How do you test a real database?**
> "Testcontainers with the same database engine, run migrations, seed data, and assert persistence
> and query behavior. Use a fresh container/schema per run for isolation."

**D4. How do you test downstream failures?**
> "WireMock or a stub server: success, 4xx/5xx, timeout, malformed payload, retry/backoff, and
> circuit breaker. Assert the service degrades or fails as designed."

**D5. What is a slice test?**
> "A test that loads only part of the Spring context — web, JPA, JSON, etc. It is faster than a full
> context and still tests the integration with that slice. It does not catch missing beans outside
> the slice."

**D6. How do you keep the suite fast?**
> "Mostly unit and slice tests, a few full integrations, Testcontainers reused per class, parallel
> execution with isolated data, and slow tests in a separate stage."

## E. Production concerns

**E1. How do you handle auth?**
> "Spring Security with token validation, method/URL authorization, and tests for 401 vs 403, owner
> vs non-owner, and expired/invalid tokens. Do not leak whether a resource exists in auth errors."

**E2. How do you handle timeouts and retries?**
> "Set connect/read timeouts on every outbound call, retry only idempotent/transient operations with
> backoff and jitter, and use a circuit breaker for failing dependencies. Test the failure path."

**E3. How do you observe a service?**
> "Structured logs with correlation IDs, metrics for request/latency/errors/dependencies, health
> probes, and traces. A test failure should link to a trace, not just a stack trace."

**E4. How do you handle graceful shutdown?**
> "Stop accepting new requests, finish in-flight work within a deadline, close connections, and let
> readiness fail first. Test with a rolling deploy and in-flight requests."

**E5. How do you prevent duplicate writes?**
> "Idempotency keys, unique constraints, and transactional outbox where events are involved. Test
> duplicate and concurrent requests."

**E6. What would you check before a release?**
> "Health/readiness, migrations, config/secrets, auth, one read/write per critical API, downstream
> integration, error rate/latency, and rollback. The same artifact that passed tests is the one
> deployed."

## F. Scenario questions

**F1. The service starts but all requests return 500. What do you check?**
> "Startup logs and the health endpoint, bean wiring, config/secrets, database connectivity, and the
> first exception in the logs. Then reproduce with a slice/integration test."

**F2. A test passes locally but fails in CI. What do you check?**
> "Time zone/locale, database dialect, ports, env vars, test order/shared state, file paths, and
> dependency versions. CI should use the same profile and container images."

**F3. A query is slow only in production. What do you do?**
> "Check data volume, indexes, N+1, query plan, pagination, and cache hit rate. Reproduce with
> production-like cardinality, not just a few rows."

**F4. How would you add a new endpoint safely?**
> "Design the contract, add validation/error cases, write a web slice test, add a repository test if
> data changes, add an integration test for wiring, update docs, and add a smoke check for release
> validation."

**F5. How would you refactor a controller with business logic?**
> "Extract the rules into a service, keep the controller for HTTP/validation, add unit tests around
> the service and slice tests around the controller, then verify behavior is unchanged."
