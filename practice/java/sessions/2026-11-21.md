# Session 3 — 2026-11-21 — Enums

Starting point: user asked for core Java, starting with enums. Enums were not in the matrix, so this

asked and the `Person` drill depends on a status field anyway.

## Taught

1. **An enum is a class with a fixed number of instances** — each constant is created once at class
   init, so `==` is safe, `equals` adds nothing, and `new` is a compile error.
2. **Constants can carry state and behavior** — fields, a constructor (implicitly `private`), and
   methods; a semicolon is required after the last constant when members follow.
3. **`name()` vs `toString()` vs `valueOf`** — `name()` is the constant, `toString()` is display and
   overridable, `valueOf` parses `name()` and throws `IllegalArgumentException` on anything else.
4. **`ordinal()` is a declaration index, not an id** — reordering or inserting a constant silently
   renumbers persisted data.
5. **`switch` over an enum is compile-checked** — Java 17 switch expressions must be exhaustive or
   carry `default`.
6. **`EnumSet` / `EnumMap`** — compact, ordinal-ordered, faster than `HashSet`/`HashMap` for enums.
7. **SDET angle** — `TestStatus` beats `String status`: typos become compile errors; JPA needs
   `@Enumerated(EnumType.STRING)` so the name, not the ordinal, is stored.

## Corrections

**Q1 (0/4).** `println` calls `toString` → `fail`. `name()` → `FAIL`. `valueOf("fail")` throws
`IllegalArgumentException: No enum constant Status.fail`. Model: `valueOf` parses the **constant
name**, not the display text; overriding `toString` does not teach `valueOf` anything. Trap: the two
strings look interchangeable in code and are not.

**Q2 (3/4).** Right model — `==` compares references, `.equals()` compares content, `new String`
creates a distinct object. Missing half: enums are safe because the class guarantees exactly one
instance per constant, so reference equality and value equality always agree. Also missing: string
**literals are interned**, so `==` on literals is accidentally `true` — the bug is intermittent, not
constant. Trap: "enums and Strings are both reference types" is true and still leads to opposite
rules.

**Q3 (0/4).** Ordinals are positions. Inserting `SKIPPED` first moves `FAIL` from 1 to 2
(`EnumShift` run: `before: FAIL=1`, `after: FAIL=2`), so a stored `1` that used to mean `FAIL` now
reads `PASS`. `values().length` and `switch` are unaffected; `EnumMap`/`values()` iteration order
changes. Store `name()`, not `ordinal()` — or better, `@Enumerated(EnumType.STRING)`.

## Misconceptions found

- `valueOf` reads whatever `println` prints → it reads `name()`, case-sensitive, and throws.
- `ordinal()` is an id → it is a declaration index; inserting a constant silently renumbers saved
  data.
- `==` on a reference type is always wrong → it is wrong only when more than one instance can share
  the same value; enums, and interned literals, are the exceptions that hide the bug.

## Taught

   `getOrDefault` + `put` shape. One line, no null check.

3. **`indexOf('@')` vs `split("@")`** — `indexOf` + `substring` for one delimiter and a validity check;
   `split` takes a regex, so `"@"` is literal but `"."` is not.
4. **Complexity one-liner** — `ArrayList.get(i)` is O(1); `LinkedList.get(i)` is O(n).
