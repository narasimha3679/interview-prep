# Session 4 — 2026-11-22 — Arrays, in-place reverse

## Taught

1. **Swapping needs a temp** — `a[j] = a[i]` destroys the value at `j` before it can be moved.
2. **Pointers must meet** — reversing swaps the two ends and walks inward until `i < j` fails; a loop
   over the whole length re-copies already-overwritten slots.

Demo: learner's own file, output below.

## Attempt 1 — `ReverseArray` (compiles, wrong output)

Code as written:

```java
for (int i = a.length - 1, j = 0; i >= 0; i--, j++) {
    a[j] = a[i];
}
```

Actual output: `[5, 4, 3, 4, 5]` (expected `[5, 4, 3, 2, 1]`). Score 2/4 — right idea (two ends),
compiles, but overwrites and never stops at the middle.

## Correction

The first copy `a[0] = a[4]` destroys the `1`; the later `a[4] = a[0]` copies the `5` that replaced
it. Same reason a swap needs a temp:

```java
for (int i = 0, j = a.length - 1; i < j; i++, j--) {
    int t = a[i];
    a[i] = a[j];
    a[j] = t;
}
```

Reference verified: `[5, 4, 3, 2, 1]` and `[40, 30, 20, 10]`.

## Attempt 2 — `ReverseArray` with `while` (compiles, correct)

```java
int start = 0, end = a.length - 1;
while (start < end) { int t = a[start]; a[start] = a[end]; a[end] = t; start++; end--; }
```

Output: `[5, 4, 3, 2, 1]`. Score 4/4; `int[]` in-place swap now solid.

## Mock 1 — summary

| Task | Score | Time | First-attempt correct? |

| B second largest | 4/4 | 7 min + 3 fixes | no |

Pattern: algorithms are right; the losses are syntax (`()` on methods), types (`Map.Entry` vs `Map`),
and sentinels (`0` as "not found"). None of those are interview-hard — they are "compile and test
before saying done" problems.

One trap to remember: `count.get(c) == 1` is safe because `1` is an `int`, so Java unboxes. But
`count.get(a) == count.get(b)` compares two `Integer` **objects** and is wrong above 127 — use
`.equals` or `intValue()`.

**B. `SecondLargest`** — 7 min, compiles, but `{10, 20}` prints `-` instead of `10`. 2/4.

Cause: on a new largest the old largest is dropped — it should become `second`. `{3,7,7,5,1}` passed
by luck because `5` came after the `7`. Second bug: `second == 0` is used as "not found", but `0` can
be a real value (`{0, 5}` → `0`). Fix verified with `Integer.MIN_VALUE` as the empty marker plus
`second = largest` on every promotion.

```java
if (n > largest) { second = largest; largest = n; }
else if (n > second && n != largest) { second = n; }
```

Attempt 2: added `second = largest` but dropped the `else if`, so `{3,7,7,5,1}` → `7` and
`{4,4,4}` → `4`. Numbers that are not a new maximum are ignored, and duplicates promote themselves.
Still 2/4.

Attempt 3: `else if (n > second & n != largest)` — `>=` fixed, `else` restored, `{3,7,7,5,1}` → `5`,
`{4,4,4}` → `-`, `{10,20}` → `10`. 4/4 on the spec.

Two risks left: single `&` should be `&&` (no short-circuit, reads as a bitwise operator); and
`largest = second = 0` breaks on zeros and negatives — verified `{0,5}` → `-` (should be `0`) and
`{-5,-2}` → `-` (should be `-5`). Fix: `Integer.MIN_VALUE` for both, and compare against it.
