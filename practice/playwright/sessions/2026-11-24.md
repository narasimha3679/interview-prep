## Session 2 — basics, unit 1

Previous Q1–Q5 were issued cold, before any teaching, and were never answered. Restarted at zero with
a taught unit instead of a cold quiz.

### Taught

1. **A test is a function with fixtures** — `test('name', async ({ page }) => …)`. The argument object
   is the dependency graph; `page` is one isolated tab.
2. **A locator is a query, not an element** — `page.getByRole(...)` stores the query. The DOM is read
   only when the locator is acted on or asserted.
3. **Actions and assertions auto-wait** — `click`/`fill` wait for actionability; `expect(locator)`
   polls. That is why `waitForTimeout` and `isVisible()` checks are wrong in this tool.

Demo: `npx playwright test --project=ui --grep "@smoke"` → **3 passed (5.0s)**, setup project included.

| 3 | A button renders 1.5s after load. Predict the click with no sleep. | "builtin wait instead of failing it waits until default timeout; if it loads it checks loaded, visible, enabled and clicks" | 3 |

### Corrections

**Q1 (3/4).** Correct, including the lifecycle. Precision to add: the fixture is built from the running
project's `use` block (browser, context options, `storageState`), and it is **per test**, not per
worker. The context is the isolation boundary — cookies and storage live there, which is exactly why
auth state is injected at context creation.

**Q2 (3/4).** Right mechanism, wrong term. "Lazy load" describes images; this is a **lazy query**.
`getByRole` returns a `Locator` handle and reads the DOM only at action/assert time. It does not
cache a node — it re-asks every time, which is both what kills staleness and what makes strict mode
possible (two matches → error, not "pick the first").

**Q3 (3/4).** Right. Complete the actionability list: visible, **stable** (animation finished),
enabled, **receives events** (nothing covering it), plus editable for `fill`. It retries the lookup
*and* the checks until `actionTimeout`, then fails. Requested trace: `click` → wait for actionable →
click.

**Q4 (2/4).** The guess is half right, and the missing half is the whole point. `isVisible()` answers
**immediately** with a boolean. It does not wait. So a slow render returns `false` and the test goes
red while the app is fine. `await expect(locator).toBeVisible()` polls until the timeout and, on
failure, prints the locator, the actual state and a DOM snapshot. A boolean snapshot cannot retry.

Trap: `isVisible()` is a photograph; `expect(locator)` is a retry loop with a diagnostic attached.

### Misconceptions found

- "Locators lazy-load" → locators are lazy *queries*; nothing is cached, nothing is pre-fetched.
- Auto-wait is not "wait for page load" → it retries the locator resolution and re-checks
  actionability per action.
- `isVisible()` seen as a wait → it is a one-shot snapshot; the waiting lives in web-first assertions.

### Locator question — login fields

Verified on the live page (not assumed): `input#email` (type=email), `input#password` (type=password),
both with `label[for]` associations, clicking the label moves focus to the field, no `aria-label`, no
`aria-labelledby`, zero test ids.

Ranking given: `getByLabel` first (it uses the same association a screen reader does and fails if the
label breaks); then `getByRole('textbox', { name })` — valid for email but does **not** match password
fields; then `#id`; then `getByPlaceholder` (placeholder is a hint, not the accessible name); then
`input[type=email]`; never XPath/nth. Test ids only where no accessible name exists or the name is
duplicated.

**Correction (same session).** I said password inputs have no `textbox` role. That is true of the
ARIA spec, but **Playwright's role engine maps `input[type=password]` to `textbox`**, and its own
error output suggested it. Verified on the live page: `getByRole('textbox', { name: 'Password' })`
→ 1 match. The tool's behaviour is what the locator must survive, not the spec.

### Strict-mode failure — `getByLabel('Password')` matched 2 elements

Learner's setup failed at `getByLabel('Password').fill(...)` with a strict mode violation: the field
and the eye toggle (`<button aria-label="Show password">`). Cause: `getByLabel` consults associated
labels **and** `aria-label`, and matching is case-insensitive substring by default, so "Show password"
contains "Password".

Verified counts on live: `getByLabel('Password')` → 2; `getByLabel('Password', { exact: true })` → 1;
`getByRole('textbox', { name: 'Password' })` → 1; `getByPlaceholder('Password')` → 1.

Taught: strict mode is a feature — ambiguity fails at the first action instead of silently filling
the wrong element; the earlier `getByPlaceholder` pass was luck, not correctness. Fix: `exact: true`
on both label locators.
