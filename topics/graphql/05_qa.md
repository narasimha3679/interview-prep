# 05 — GraphQL Q&A

Cover the answer, say your version out loud, then compare.

---

## A. Fundamentals

**A1. What is GraphQL?**
> "A typed query language and runtime for APIs. The client sends a query document describing the
> fields it needs, and the server resolves them against a schema. It reduces over- and under-fetching
> and lets one request traverse relationships."

**A2. How is GraphQL different from REST?**
> "REST is resource/endpoint-centric; GraphQL is schema/query-shape-centric. REST uses HTTP status
> codes and server-defined payloads. GraphQL usually has one endpoint, returns `data` plus `errors`
> even on 200, and lets the client choose the shape. That changes how I assert responses and how I
> test authorization and performance."

**A3. Query vs mutation vs subscription?**
> "Query reads, mutation writes, subscription streams events. Queries should be side-effect free;
> mutations are for changes; subscriptions need connection lifecycle and event-filter tests."

**A4. What is a resolver?**
> "A function that returns the data for a field. Resolvers are where N+1, auth, and error handling
> live, so they are a key test target."

**A5. What is the schema?**
> "The type system: types, fields, arguments, nullability, enums, interfaces, unions, queries, and
> mutations. It is the contract. I diff it in CI and fail on breaking changes."

**A6. What is introspection?**
> "A GraphQL query that describes the schema (`__schema`, `__type`). It powers tooling and schema
> checks. Many teams disable it in production to reduce exposure."

## B. Testing

**B1. How do you test a GraphQL API?**
> "I test at three levels. Schema: diff and validate. Operation: queries/mutations with variables,
> fragments, aliases, directives, and error cases. System: auth, pagination, N+1/cost, caching,
> subscriptions, and integration with downstream services. I assert `data` and `errors` separately
> and never rely on HTTP 200 alone."

**B2. Why is HTTP 200 not enough?**
> "GraphQL can return 200 with an `errors` array and partial or null data. A status-only assertion
> passes while the client is broken. I assert the error code, path, and data shape."

**B3. How do you test partial failures?**
> "Construct a query with multiple fields where one resolver fails. Assert that the successful
> fields return data, the failing field is null or absent, and `errors[]` contains the path and a
> stable code. This verifies nullability propagation."

**B4. How do you test nullability?**
> "For each non-null field, force a null/failure and assert the error bubbles to the nearest nullable
> parent. Check `data`, `errors[].path`, and the resulting shape. Also test optional fields returning
> null without errors."

**B5. How do you test GraphQL auth?**
> "Endpoint token required, operation-level permission, field-level redaction, node ownership, and
> tenant isolation. I test anonymous, owner, non-owner, admin, expired token, and wrong scope. The
> key is that a query can be allowed while a nested field leaks data."

**B6. How do you test pagination?**
> "First page, middle page, last page, beyond-end, invalid cursor, size limits, stable ordering, and
> no duplicates or gaps across pages. For cursor pagination, assert `pageInfo` consistency."

**B7. How do you test N+1?**
> "Measure latency as the parent count grows and instrument downstream calls. If 50 parents cause 50
> queries, that's N+1. The fix is batching/DataLoader. In CI I assert a query-count budget or a
> relative latency threshold, not a hardcoded millisecond value."

**B8. How do you test subscriptions?**
> "Connect with auth, subscribe to a filter, publish an event, assert delivery, assert no delivery
> for other users/tenants, test reconnect and missed-event behavior, and test slow consumers."

**B9. How do you test file uploads?**
> "GraphQL file upload is usually the multipart request spec or a separate REST endpoint. Test
> content type, size limits, checksum, filename sanitization, virus scanning, and authorization."

**B10. How do you test mutations for idempotency?**
> "Send the same mutation twice with the same idempotency key and assert one side effect. If the API
> doesn't support idempotency, document the risk and test duplicate-submit behavior from the UI."

## C. Schema and compatibility

**C1. What is a breaking GraphQL schema change?**
> "Removing or renaming a field, changing a type, changing an argument type, making an optional
> argument required, removing an enum value, making a nullable field non-null, or removing an
> interface/union member. Adding fields or optional arguments is usually safe."

**C2. How do you prevent breaking changes?**
> "Check the schema into the repo, diff it in CI, fail on breaking changes, deprecate before removing,
> and give consumers a migration window. Additive changes first."

**C3. How do you version a GraphQL API?**
> "Prefer continuous schema evolution over URL versions: additive changes, deprecation, and a
> migration window. If you need versions, expose them at the gateway or via persisted operations."

**C4. What is a persisted query?**
> "A pre-registered query identified by a hash. The client sends the hash instead of the full
> document. It reduces payload size, enables allowlisting, and improves caching/security."

**C5. How do you test schema changes?**
> "Diff the SDL, run consumer contract tests, run query smoke against the new schema, and verify
> deprecated fields still work until the removal date."

## D. Performance and security

**D1. How do you protect a GraphQL API from expensive queries?**
> "Depth limits, complexity/cost limits, pagination caps, timeouts, persisted queries, rate limits,
> and alias limits. I test that each control rejects before execution with a clear error."

**D2. What is query complexity?**
> "A cost assigned to fields/arguments, often based on list size and nesting. The server rejects a
> query above a budget. It prevents a single query from exhausting resources."

**D3. How do you test rate limiting?**
> "Send requests above the limit and assert 429 or an error code with retry guidance. Also test that
> the limit is per user/tenant, not global, and that legitimate bursts are allowed."

**D4. What GraphQL-specific security risks exist?**
> "Field-level data leakage, introspection exposure, expensive/deep queries, alias abuse, batching
> abuse, injection through arguments, and authorization bypass via nested fields. The OWASP API
> Top 10 still applies."

**D5. How do you test caching?**
> "Persisted queries, CDN caching of GET queries, field-level cache, and cache invalidation after a
> mutation. Assert stale data is not served beyond the documented window."

## E. Scenario questions

**E1. A GraphQL query returns 200 but the UI shows an error. What do you check?**
> "The `errors` array, `data` shape, nullability propagation, and the operation name. Then the
> resolver logs/trace for the failing path."

**E2. A nested query is fast in staging but slow in production. Why?**
> "Data volume changes the N+1 cost. Check downstream query counts, pagination caps, resolver
> batching, cache hit rate, and database indexes. Reproduce with production-like cardinality."

**E3. A client says a field disappeared after a deploy. How do you prevent it next time?**
> "Schema diff in CI, consumer contract tests, deprecation policy, and a schema registry/checks
> artifact. Additive changes only; removal after a migration window."

**E4. How would you test a GraphQL gateway over multiple services?**
> "Test each subgraph's schema and resolvers, the gateway's schema composition, field routing,
> partial failure, auth propagation, and N+1 across subgraphs. Contract-test the subgraph schemas."

**E5. How do you test GraphQL in CI without a full environment?**
> "Schema diff and unit tests on resolvers locally; a lightweight GraphQL server or mock for
> operation tests; full integration against an ephemeral environment for release validation."
