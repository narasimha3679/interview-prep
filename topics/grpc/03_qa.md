# 03 — gRPC Q&A

**G1. What is gRPC?**
> "An RPC framework using HTTP/2 and Protobuf. The `.proto` file defines services and messages; clients
> call methods like local functions. It is fast, strongly typed, and supports streaming."

**G2. gRPC vs REST?**
> "REST is resource/HTTP-semantics oriented and human-readable JSON. gRPC is contract-first, binary,
> HTTP/2, and supports streaming. gRPC is common for internal service-to-service calls; REST is common
> for public/browser APIs."

**G3. What are the call types?**
> "Unary (one request/one response), server streaming, client streaming, and bidirectional streaming.
> Each has a different test shape, especially around closing/cancellation."

**G4. How do you test a unary call?**
> "Build the request with the generated stub, call with a deadline, assert the response and gRPC status
> code. Test success, invalid input, not found, auth, and timeout."

**G5. How do you test server streaming?**
> "Consume the iterator until completion, assert count/order/content, test empty stream, error
> mid-stream, and client cancellation. Always bound the test with a timeout."

**G6. How do you test bidirectional streaming?**
> "Send and receive concurrently with a latch/future, assert ordering per direction, test half-close,
> cancellation, and backpressure. Never block forever."

**G7. What are gRPC status codes?**
> "`OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `RESOURCE_EXHAUSTED`,
> `FAILED_PRECONDITION`, `ABORTED`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `INTERNAL`, etc. I assert the
> code and the structured details."

**G8. How do you handle auth?**
> "Metadata carries the token; an interceptor validates it. I test missing/expired/wrong-scope tokens,
> owner vs non-owner, tenant isolation, and metadata propagation."

**G9. What is a deadline?**
> "A per-call timeout. It propagates to downstream calls. I test that a slow server returns
> `DEADLINE_EXCEEDED` and that work is cancelled."

**G10. How do you test Protobuf compatibility?**
> "Lint and diff the `.proto`, fail on field-number reuse/type changes, generate clients from the same
> schema, and use Buf/schema registry checks."

**G11. Why are field numbers important?**
> "They identify fields on the wire. Reusing or changing a number breaks compatibility. Removed
> numbers should be reserved."

**G12. How do you manually call a gRPC service?**
> "grpcurl with reflection or proto files, e.g., `grpcurl -plaintext -d '{\"id\":\"1\"}' host:port
> package.Service/Method`. Postman/BloomRPC also work."

**G13. How do you load-test gRPC?**
> "ghz or a generated client with a realistic mix, deadlines, and streaming behavior. Measure p95/p99,
> error codes, and resource saturation."

**G14. What is reflection?**
> "A service that exposes the schema so tools can discover methods. Many teams disable it in
> production; then you pass the proto files to grpcurl."

**G15. How do you test error details?**
> "gRPC can attach `google.rpc.Status` details like `BadRequest.FieldViolation` or `RetryInfo`. I
> assert the detail type and fields, not just the message string."

**G16. What breaks gRPC compatibility?**
> "Changing a field type, reusing a field number, changing an enum number, renaming a service/method,
> or changing semantics. Adding fields/enum values/methods is usually safe."

**G17. How do you test cancellation?**
> "Cancel the call/stream from the client and assert the server stops work and releases resources. For
> streaming, assert the stream closes and no further messages arrive."

**G18. What is backpressure?**
> "The consumer is slower than the producer; the stream must apply flow control rather than buffer
> unboundedly. Test a slow consumer and assert memory/latency stay bounded."

**G19. gRPC vs GraphQL?**
> "gRPC is method-oriented RPC with Protobuf; GraphQL is a query language with client-selected fields.
> gRPC is common internal/service-to-service; GraphQL is common for client-facing aggregation."

**G20. What would you test first?**
> "The contract and the critical unary methods, then auth/deadlines, then streaming and
> compatibility. Streaming is where the subtle bugs are, but it is not the first thing to automate."
