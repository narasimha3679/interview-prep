# 05 — Mobile Q&A

**M1. Native vs hybrid vs mobile web?**
> "Native uses platform SDKs and gives the best performance/device APIs. Hybrid wraps web content in
> a native shell, so I test both native and WebView contexts. Mobile web runs in the browser and I
> can use Playwright/Selenium with device emulation. The shape decides the tooling and the risks."

**M2. How do you test a mobile app?**
> "API/component tests for business logic, Appium for native/hybrid critical journeys, Playwright for
> mobile web, and real devices for release confidence. I focus on lifecycle, permissions, network,
> deep links, push, and OS/device differences, not just the screen."

**M3. Appium vs XCUITest/UiAutomator2?**
> "Appium is cross-platform and uses the WebDriver protocol. XCUITest/UiAutomator2 are platform-native
> and faster but single-platform. I choose based on app shape, team skills, and whether I need both
> platforms."

**M4. How do you handle permissions in tests?**
> "Set capabilities to auto-grant where appropriate, and have explicit tests for deny/revoke/ask-every-
> time. Permission behavior varies by OS version, so it belongs in the device matrix."

**M5. How do you test deep links?**
> "Cold start, warm start, authenticated/unauthenticated, invalid link, fallback to browser/store, and
> the destination screen. Deep links are a common entry point and often bypass normal navigation."

**M6. How do you test push notifications?**
> "Permission, delivery, payload, tap action/deep link, foreground vs background, duplicate/expired
> notification, and opt-out. Push is an external dependency, so stub/simulate where possible and
> verify on a real device."

**M7. How do you test offline/slow network?**
> "Toggle network state, throttle, abort requests, and assert loading/error/retry/cached states. Also
> test switching networks mid-request and app backgrounding."

**M8. How do you handle flaky mobile tests?**
> "Stable accessibility IDs, explicit waits, fresh app state, unique data, real-device debugging
> artifacts, and quarantine with an owner. Mobile flakiness is usually timing, device state, or
> network."

**M9. Emulator or real device?**
> "Emulators for fast PR smoke; real devices for release confidence. Emulators miss manufacturer/OS
> quirks, performance, and real network behavior."

**M10. How do you choose a device matrix?**
> "Analytics: top OS versions, manufacturers, screen sizes, locales, and performance tiers. Then tier
> the matrix: smoke, core nightly, full pre-release, exploratory for new OS/devices."

**M11. How do you test app upgrades?**
> "Install the previous version, create state, upgrade, and verify data/session migration, login,
> deep links, and no crash. Also test fresh install vs upgrade."

**M12. How do you test biometrics?**
> "Simulate success/failure/lockout, test fallback to PIN/password, and verify sensitive actions
> require re-auth. Biometrics are hard to automate; combine API-level tests with manual/device
> checks."

**M13. How do you test accessibility on mobile?**
> "Screen reader labels, focus order, touch target size, contrast, font scaling, and reduced motion.
> Use platform accessibility inspectors plus manual screen-reader passes."

**M14. How do you test mobile performance?**
> "App startup, screen render, scroll smoothness, network latency, memory, battery, and crash/ANR
> rates. Use platform profilers and real devices; emulators are not representative."

**M15. How do you test mobile security?**
> "Secure storage/keychain, certificate pinning, session timeout, biometric gating, jailbreak/root
> detection, PII in logs/screenshots, and deep-link/auth bypass. Combine static analysis, dynamic
> testing, and manual review."

**M16. How do you integrate mobile tests into CI?**
> "Build the app, run unit/API tests, smoke on emulators, then real-device smoke on merge and full
> matrix nightly/pre-release. Publish video/logs/screenshots and device metadata."

**M17. What would you not automate on mobile?**
> "Usability, visual design judgment, exploratory device testing, and highly device-specific gestures.
> Automation is for stable, repeatable critical flows."

**M18. How do you test a React Native/Flutter app?**
> "Same strategy: API/component tests for logic, Appium/Detox/Maestro for UI, real devices for release.
> Watch for bridge/native-module bugs and platform-specific rendering."

**M19. How do you test in-app purchases?**
> "Sandbox accounts, product catalog, purchase success/cancel/failure, restore, subscription renewal/
> expiry, receipt validation, and duplicate purchase. Test on both platforms."

**M20. A test passes on an emulator but fails on a real device. What do you check?**
> "OS/manufacturer differences, performance/timing, permissions, keyboard, network, screen size, and
> device logs. Reproduce on the same device and capture video/logs before changing the test."
