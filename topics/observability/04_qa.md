# 04 — Observability Q&A

**O1. What are the three pillars of observability?**
> "Logs, metrics, and traces. Metrics tell me something is wrong and how big; traces tell me where;
> logs tell me why. I use them together, not as substitutes."

**O2. What is a correlation ID?**
> "An ID attached to a request and propagated through every service and message. When a test fails, I
> query logs/traces by that ID instead of guessing. It is the thread that ties a distributed request
> together."

**O3. Correlation ID vs trace ID?**
> "A trace ID is the OpenTelemetry/W3C identifier for a distributed trace. A correlation ID is a
> broader application-level ID I can attach to a test run or business flow. Often they are the same,
> but I treat the correlation ID as the test-friendly handle."

**O4. How do you test observability?**
> "Assert that the request emits the expected log fields, metric, and span; that the trace includes
> downstream calls; that failures set error status; and that no secrets/PII leak. I also test that a
> failing request can be found by its correlation ID."

**O5. What is a span?**
> "One operation in a trace, with a name, start/end time, status, attributes, and parent. Spans show
> the request path and where time/failure occurred."

**O6. What are the four golden signals?**
> "Latency, traffic, errors, and saturation. They cover the user-visible health of a service."

**O7. What is high cardinality, and why does it matter?**
> "A metric label with many unique values — user ID, order ID, request ID. It explodes storage and
> query cost. I keep labels low-cardinality and put unique IDs in logs/traces."

**O8. What is OpenTelemetry?**
> "A vendor-neutral standard for traces, metrics, and logs: APIs/SDKs, context propagation, a
> collector, and semantic conventions. Instrument once, export to any backend."

**O9. What is trace context propagation?**
> "Passing the trace/span identifiers across service boundaries — HTTP headers like `traceparent`,
> message attributes, gRPC metadata. Without it, each service starts a new trace."

**O10. Head vs tail sampling?**
> "Head sampling decides at trace start and is cheap but may drop rare errors. Tail sampling decides
> at the end and can keep all errors/slow traces, but needs buffering. I always retain error and slow
> traces."

**O11. How do you debug a failure across services?**
> "Get the correlation/trace ID, check metrics to see scope, open the trace to find the failing/slow
> span, read logs for that service/span, compare environment/version, reproduce, then classify the
> root cause as product/test/data/environment/dependency/platform."

**O12. A test fails only in CI. What evidence do you need?**
> "The test report, request/response, correlation ID, trace link, service logs, environment/version,
> and a screenshot/trace for UI. Without evidence, a re-run is just gambling."

**O13. How do you link a UI failure to backend telemetry?**
> "Capture the network request's correlation/trace header from the browser trace, then query the
> backend by that ID. Playwright traces include network activity, which makes this possible."

**O14. What would you assert about logs?**
> "Structured fields and stable event names, not exact prose. I assert the error code, correlation ID,
> and absence of secrets/PII. Prose changes; fields are the contract."

**O15. How do you test a metric?**
> "Emit the operation, then assert the metric exists with the expected name/labels and a value delta.
> In unit tests, use an in-memory registry; in integration, query the metrics endpoint/backend."

**O16. How do you test a trace?**
> "Use an in-memory exporter in unit tests and assert span names, parent/child relationships, status,
> and attributes. In integration, send a request and query the tracing backend by trace ID."

**O17. What is an SLO?**
> "A service-level objective — a target for reliability, e.g., 99.9% of requests under 300ms over 30
> days. The error budget is the allowed failure. Release gates can use error-budget burn."

**O18. How do you use observability in release validation?**
> "Compare error rate, latency, saturation, and business metrics before/after the canary. If the new
> version burns the error budget or shows new exceptions, roll back. Technical metrics alone are not
> enough; check the business metric too."

**O19. What is a synthetic check?**
> "An automated probe that exercises a critical journey from outside the system. It catches
> availability and end-to-end breakage that internal metrics may miss."

**O20. What is the biggest observability mistake in test frameworks?**
> "Producing a red result without evidence. If the report doesn't link to a trace, log, screenshot, or
> response, the failure will be re-run instead of diagnosed."
