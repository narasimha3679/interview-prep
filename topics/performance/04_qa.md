# 04 — Performance Q&A

**P1. How do you approach performance testing?**
> "Start from the SLO: latency, throughput, error rate. Model a realistic traffic mix with think time,
> run in an isolated production-like environment, collect client and server metrics, and find the
> first bottleneck. Then fix and repeat. A load test without a target is just a demo."

**P2. What metrics matter?**
> "p95/p99 latency, throughput, error rate, concurrency, CPU, memory, GC, DB connections, queue
> depth, and saturation. Averages hide the tail, so I report percentiles."

**P3. Load vs stress vs soak vs spike?**
> "Load is expected peak; stress is beyond expected to find the breaking point; soak is long-duration
> to find leaks/degradation; spike is a sudden burst to test autoscaling/queue behavior."

**P4. What is Little's Law?**
> "Concurrency = throughput × latency. It explains why latency increases as concurrency grows and why
> a system saturates when the in-flight work exceeds its capacity."

**P5. How do you find a bottleneck?**
> "Correlate latency with resource metrics: CPU, memory/GC, DB connections/locks, thread pool, network,
> queue lag. The bottleneck moves as you fix it; keep measuring."

**P6. Why are averages misleading?**
> "A few slow requests can be hidden by many fast ones. The average looks fine while p95/p99 users have
> a bad experience. Percentiles reflect the tail."

**P7. How do you design a load profile?**
> "Model real user behavior: traffic mix, think time, ramp-up, steady state, peak, and ramp-down. Use
> production analytics for the mix and volume; don't hammer one endpoint."

**P8. How do you avoid the load generator becoming the bottleneck?**
> "Run it on a separate machine/container, monitor its CPU/network, use distributed generators for
> high load, and keep it out of the system under test."

**P9. How do you make performance tests reliable in CI?**
> "Isolated environment, fixed profile, warm-up, baseline comparison with tolerance, 2–3 runs for
> critical gates, and separation of regression from environment noise. Full benchmarks run nightly,
> not on every PR."

**P10. What is a performance budget?**
> "A threshold that fails the build, e.g., p95 < 300ms, p99 < 800ms, error rate < 0.1%, or no >10%
> regression versus baseline. It turns performance into a testable contract."

**P11. How do you test autoscaling?**
> "Ramp load beyond current capacity, observe scale-out latency, verify new instances become ready,
> measure whether the SLO is met during scaling, then scale-in and check for dropped requests."

**P12. How do you test a queue/consumer?**
> "Measure publish rate, consumer lag, processing latency, error rate, and DLQ count under load. Test
> burst, sustained, and consumer failure scenarios."

**P13. How do you test a database under load?**
> "Production-like data volume, realistic query mix, connection pool limits, index/query plans, lock
> contention, and read/write ratio. Watch for N+1 and slow queries."

**P14. What is a soak test for?**
> "Finding memory leaks, connection leaks, log growth, cache degradation, and gradual latency
> increases over hours. Short load tests miss these."

**P15. How do you report performance results?**
> "Version, environment, data size, load profile, p50/p95/p99, throughput, error rate, resource
> graphs, bottleneck, and comparison to baseline. A graph without context is not a result."

**P16. A performance test passes locally but fails in CI. What do you check?**
> "Environment size/config, data volume, other jobs running, network, load generator resources,
> warm-up, and version differences. CI is rarely equivalent to local."

**P17. How do you test resilience under load?**
> "Inject latency/errors into a dependency while under load, and assert timeout, retry, circuit
> breaker, degradation, and recovery. Performance and resilience are related but distinct."

**P18. When would you not run a performance test?**
> "When there is no SLO, no production-like environment, or no owner to act on the result. A noisy
> test that nobody trusts is worse than no test."

**P19. How do you test frontend performance?**
> "Core Web Vitals (LCP, INP, CLS), page load, bundle size, network waterfalls, and real-user
> monitoring. Lighthouse/Playwright can catch regressions; field data is the truth."

**P20. What is the first thing you'd optimize?**
> "The bottleneck the data points to, not the code that looks slow. Usually it's a query, an N+1, a
> connection pool, a synchronous call, or GC — measured, not guessed."
