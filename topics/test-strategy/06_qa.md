# 06 — Test Strategy Q&A

Cover the answer, say your version out loud, then compare.

## A. Strategy

**A1. How do you build a test strategy for a new feature?**
> "Start with the risks: what can lose money, leak data, break auth, or corrupt state. Map each risk
> to the cheapest level that can catch it — unit, component, contract, API, UI, or E2E. Then define
> the data, environment, oracle, and release gate. I keep E2E for the few journeys where integration
> itself is the risk."

**A2. What is the test pyramid?**
> "A portfolio: many fast unit tests, fewer component/integration tests, a thick contract layer for
> services, and very few E2E tests. The shape is a guideline; the principle is to push coverage to
> the cheapest level that can detect the defect."

**A3. Why not test everything E2E?**
> "E2E is slow, flaky, expensive, and a failure doesn't tell you which service broke. In
> microservices it's owned by everyone, which means no one. Contracts and component tests give
> faster, attributable feedback."

**A4. How do you decide what to automate?**
> "Automate high-value, repetitive, deterministic checks: regression, critical paths, contracts,
> data-driven cases. Keep manual for exploratory testing, usability, visual judgment, and one-off
> changes. Automation buys regression safety; humans buy discovery."

**A5. What is risk-based testing?**
> "Ranking tests by probability × impact. A payment path gets more negative, concurrency, and
> resilience coverage than a read-only label. It prevents equal effort on unequal risk."

**A6. What is shift left/right?**
> "Shift left: quality earlier — contracts, unit/component tests, design reviews. Shift right:
> testing in production — canaries, synthetic checks, feature flags, observability. They complement
> each other."

**A7. How do you know your test suite is good?**
> "Escaped defects, flaky rate, feedback time, and change failure rate. Coverage is a smell, not a
> target. A suite that is slow or unreliable stops being run, so trust matters more than test count."

**A8. What would you not automate?**
> "Exploratory discovery, usability judgment, visual design approval, and high-risk one-off
> decisions. I'd also avoid automating a flow that changes every week until it stabilizes."

## B. Test levels

**B1. Unit vs component vs integration?**
> "Unit isolates one class/function. Component tests one service with its real infrastructure
> (DB/broker) and stubs neighbors. Integration wires multiple real components together. Each catches
> a different class of defect."

**B2. What is a contract test?**
> "It verifies a provider still satisfies what each consumer needs without running both. It catches
> breaking API/schema changes cheaply. It does not prove real wiring or end-to-end behavior."

**B3. What is the difference between smoke and regression?**
> "Smoke is a tiny go/no-go check after a deploy. Regression is a broad check that existing behavior
> still works, usually nightly or pre-release. Smoke is not a small regression suite."

**B4. When is an E2E test justified?**
> "When the integration itself is the risk: a critical business journey across services, a payment
> flow, a checkout. It should be few, stable, and owned."

**B5. How do you test a microservice?**
> "Unit for logic, component with Testcontainers for real infra, contract for interfaces, API for
> behavior, and a few E2E journeys through the gateway. Plus resilience and observability."

**B6. How do you test a UI?**
> "API setup, UI only for UI-specific risk: rendering, navigation, validation, accessibility. Stable
> selectors, auto-waiting, isolated context, traces on failure."

**B7. How do you test async flows?**
> "Trigger the action, poll for eventual state with a timeout, assert the payload/schema, test
> duplicate delivery for idempotency, and verify the dead-letter queue. Never assert immediately."

## C. Test design

**C1. What techniques do you use to design cases?**
> "Equivalence partitioning, boundary values, decision tables, state transitions, pairwise
> combinations, negative testing, and exploratory charters. I pick the technique based on the shape
> of the risk."

**C2. What is equivalence partitioning?**
> "Divide inputs into classes that should behave the same, then test one representative per class
> plus the boundaries. It avoids testing every value."

**C3. What is boundary value analysis?**
> "Bugs cluster at edges: min, max, just inside, just outside, zero, empty, null, max length. I test
> both sides of every boundary."

**C4. When do you use a decision table?**
> "When output depends on combinations of conditions — discounts, eligibility, pricing, permissions.
> It makes the rules explicit and catches missing combinations."

**C5. When do you use state transition testing?**
> "For workflows with states: orders, payments, listings, subscriptions. Test valid transitions,
> invalid transitions, terminal states, duplicates, and concurrency."

**C6. What is pairwise testing?**
> "Cover every pair of parameter values at least once instead of the full Cartesian product. It
> catches most interaction bugs at a fraction of the combinations."

**C7. How do you test negative paths?**
> "Missing/invalid auth, wrong role/tenant, malformed input, boundaries, duplicate submission,
> out-of-order events, dependency timeout/error, partial failure, rate limits, and injection
> strings."

**C8. What is property-based testing?**
> "Assert a property over generated inputs, e.g., encode/decode round-trip, sort idempotence, totals
> equal line items plus tax. It explores inputs you wouldn't think of."

## D. Data and environments

**D1. How do you handle test data?**
> "Unique per test or isolated per run. API-driven setup where realism matters; direct seed only for
> specific states. No production PII. Cleanup automatic and verified. Isolation beats cleanup."

**D2. How do you test in parallel without collisions?**
> "Unique data per test, no shared mutable state, fresh browser context/driver, isolated DB/schema
> or namespace, and no order dependence."

**D3. What is an ephemeral environment?**
> "A short-lived environment provisioned per PR or test run from IaC, seeded, tested, and destroyed.
> It removes contention and makes failures attributable."

**D4. How do you keep environments production-like?**
> "Same artifact, config keys, database engine/version, messaging semantics, auth model, network
> boundaries, and observability. Document the differences and why they exist."

**D5. How do you handle secrets in tests?**
> "Inject from a secret store/CI secret, never commit them, mask logs, use short-lived credentials or
> managed identity, and fail fast if missing."

**D6. How do you test async data propagation?**
> "Poll for the eventual state or event with a timeout, assert the payload/schema, test duplicates
> and ordering, and check the DLQ."

## E. Flakiness and metrics

**E1. What causes flaky tests?**
> "Fixed sleeps, races, shared state, order dependence, unstable locators, animation, environment
> contention, time/randomness, resource leaks, and parallel config. Most are test-design or
> isolation problems, not product bugs."

**E2. How do you fix a flaky test?**
> "Read the artifact, reproduce, find the non-determinism, replace sleeps with condition waits,
> isolate data/state, control time/randomness, and run a stability window. Do not add a retry."

**E3. What is your quarantine policy?**
> "Detect, quarantine to a non-blocking job, assign an owner and deadline, diagnose, fix, and return
> after stability. Track quarantine age; don't let it become a graveyard."

**E4. Are retries okay?**
> "As a detector for infrastructure blips, yes. As a way to make a red suite green, no. Report
> retried-but-passed separately."

**E5. What metrics do you track?**
> "First-run pass rate, flaky rate, suite duration p95, queue time, escaped defects, quarantine age,
> change failure rate, and MTTR. Not test count or lines of test code."

**E6. How do you measure coverage?**
> "As a gap detector: untested high-risk code, sudden drops, module comparison. Not as a hard global
> percentage. Mutation testing and escaped-defect analysis are stronger signals."

## F. System design

**F1. How would you test an API gateway?**
> "Routing, auth 401/403, token expiry, rate limits per user/tenant, header/request-ID propagation,
> timeout/upstream 5xx mapping, CORS, and content-type handling. Contract-test the routes."

**F2. How would you test a message-driven flow?**
> "Publish/consume, eventual state, idempotency with duplicates, ordering, poison message to DLQ,
> retry/backoff, and event schema compatibility. Use a real broker via Testcontainers."

**F3. How would you test a cache?**
> "Hit/miss, TTL, invalidation after write, stale read window, fallback when cache is down, key
> collision, and tenant isolation."

**F4. How would you test a payment flow?**
> "Amount/tax/currency calculation, authorization, capture, refund, duplicate charge, timeout,
> provider decline, 3DS, idempotency, reconciliation, and audit trail."

**F5. How would you test search?**
> "Indexing pipeline, query/filter/sort/pagination, relevance golden set, zero results, localization,
> tenant isolation, latency, and index-down degradation."

**F6. A release passes staging but fails in production. What do you check?**
> "Config/secrets, identity/RBAC, network/private endpoints, DNS/TLS, migration, feature flags,
> deployed version, and data shape. Compare artifact digest and environment settings."

**F7. How do you test a system with no UI and no docs?**
> "Start from the contract — OpenAPI, proto, GraphQL schema, or observed traffic. Probe happy path,
> boundaries, errors, auth, idempotency. Write schema assertions to lock the shape, then add behavior
> assertions."

**F8. How do you test a system you can't fully control?**
> "Stub across boundaries you don't own, contract-test the interface, and use a real environment for
> the final validation. Document what is simulated and what is real."
